# release-guards

되돌릴 수 없는 릴리스 동작 앞에 확인 절차를 세웁니다.

> 이 문서는 [README.md](README.md)의 한국어판입니다. 내용이 어긋날 경우 영문판이 기준입니다.

```bash
/plugin marketplace add somaz94/claude-plugins
/plugin install release-guards@somaz94
```

<br/>

## 왜 필요한가

"릴리스는 내가 요청할 때만 해라"는 모델이 동의해 놓고 도구 호출 마흔 번쯤 뒤에 슬그머니 넘어서는 종류의 규칙입니다. 악의가 아니라, 빌드가 초록불이면 태그를 다는 게 자연스러운 다음 순서처럼 보이기 때문입니다.

모델이 기억해 주기를 믿는 관례는 경계선이 아닙니다. 훅은 경계선입니다. 이 두 개는 그 규칙을, 나중에 태그 목록에서 발견하는 것이 아니라 문제가 되는 바로 그 순간에 하네스가 강제하는 것으로 바꿉니다.

<br/>

## 무엇을 막는가

| 훅 | 발동 시점 | 잡는 것 |
|---|---|---|
| `pre-release-action-guard` | `Bash` | `git tag` 생성·삭제, `gh release` / `glab release` create·edit·delete·upload |
| `pre-edit-release-automation-guard` | `Edit` · `Write` · `MultiEdit` | `cliff.toml`, `RELEASE.md`, `release.yml`, `.goreleaser.yaml`, `release-please-config.json` |

두 번째가 보기보다 중요합니다. 릴리스 자동화 파일은 *생성물에 준하는* 성격이라, 저장소에 있는 `RELEASE.md`가 비어 있는 것이 정상입니다. 태그를 밀 때마다 파이프라인이 다시 쓰기 때문입니다. 사전 지식 없이 그 파일을 읽은 어시스턴트는 버그로 보고 고치고, 그 결과 다음 릴리스가 무엇을 발행할지가 조용히 바뀝니다.

<br/>

## 묻되, 막지는 않습니다

둘 다 `ask`를 반환합니다. 어느 쪽도 `deny`를 반환하지 않고, 거부를 강제하려고 비정상 종료하지도 않습니다.

이 구분이 설계의 전부입니다. 릴리스는 정당한 행위이고, 대부분의 저장소에서는 *바로 그것이 목적*입니다. 정당하지 않은 건 사용자가 말하지 않았는데 릴리스되는 상황입니다. 막는 게이트는 어시스턴트를 그 작업에 쓸모없게 만들지만, 묻는 게이트는 결정을 사용자에게 되돌려 줄 뿐이고 답이 "예"일 때 드는 비용은 키 한 번입니다.

읽기 전용 명령은 조용히 통과합니다. `git status`, `git log`, `git tag -l`은 묻지 않습니다.

<br/>

## 절대 하지 않는 것

- 동작을 차단하거나 거부하거나 취소하는 일.
- 검사한 명령을 실행하거나 수정하거나 다시 쓰는 일.
- 네트워크에 접근하거나 저장소를 건드리는 일.

훅이 실패하면 — 잘못된 입력, 읽을 수 없는 페이로드 — **열린 상태로 실패합니다.** 조용히 통과시킵니다. 오작동할 때 작업 흐름을 막는 가드는 꺼지게 되고, 꺼진 가드는 아무것도 지키지 못합니다.
