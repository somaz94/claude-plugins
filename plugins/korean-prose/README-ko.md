# korean-prose

한국어 글을 딱 한 가지 기준으로 봅니다: 사람이 쓴 한국어로 읽히는가, 아니면 한국어 단어를 입은 영어로 읽히는가.

> English documentation is at [README.md](README.md).

Claude Code 안에서:

```
/plugin marketplace add somaz94/claude-plugins
/plugin install korean-prose@somaz94
```

또는 대화형 세션 없이 셸에서:

```bash
claude plugin marketplace add somaz94/claude-plugins
claude plugin install korean-prose@somaz94
```

<br/>

## 왜 필요한가

맞춤법 검사기는 단어 하나를 읽습니다. 문법 검사기는 문장 하나를 읽습니다. 둘 다 `본 문서는 마이그레이션에 있어서 중요성을 가진다` 를 아무 말 없이 통과시킵니다. 모든 단어의 철자가 맞고 문법도 온전하기 때문입니다. 그래도 이건 아무도 쓰지 않는 한국어입니다.

번역된 문서가 사는 곳이 바로 그 틈입니다. 영어로 쓰고 한국어로 옮긴 README 는 영어 골격을 그대로 가지고 있습니다 — `의` 연쇄, 수동태, "~하는 것이 중요하다" 라는 틀. 결과물은 읽는 문서가 아니라 해독하는 문서가 됩니다. 어떤 도구도 이걸 잡아내지 못합니다. 도구가 검사하는 층위에서는 틀린 게 없기 때문입니다.

이 문제의 더 최근 절반은 번역과 아무 상관이 없습니다. **생성된** 텍스트는 자기만의 흔적을 남깁니다: 의미 없는 담화 표지, 기계적인 `첫째 … 둘째 …`, 한 문단에서 세 번 쓰인 대조 구문. 번역 관점의 눈에는 이것들이 보이지 않습니다. 번역된 것이 없기 때문입니다.

<br/>

## 무엇을 잡는가

| 패턴 | 왜 잘못 읽히는가 | 무엇이어야 하는가 |
|---|---|---|
| `~에 있어서` | 일본어 어법 잔재, 현대 한국어에서 거의 죽은 표현 | `~에서`, 또는 삭제 |
| `중요성을 가지다` | 영어 "to have importance" | `중요하다` |
| `검토 진행`, `구축 진행` | 이미 동사인 말을 명사화 | `검토했다`, `구축했다` |
| `압력을 완화` | `pressure` 를 *공기* 압력을 뜻하는 단어로 번역 | `부하를 완화` |
| `간접화` | `indirection` 을 존재하지 않는 단어로 옮김 | `분리` |
| `~하는 것이 가능하다` | "it is possible to" 의 직역 | `~할 수 있다` |
| `되어지다`, `보여지다` | 피동을 두 번 적용 | `되다`, `보이다` |
| `GitHub Actions 의` | 조사가 공백으로 제 단어와 떨어짐 | `GitHub Actions의` |

설치할 값을 하는 건 가운데 행들입니다. `압력`, `정렬`, `수렴`, `재활용`, `함정`, `완주` 는 전부 실재하는 한국어 단어이고 사전이 해당 영어 단어에 기꺼이 내주는 말입니다 — 그리고 여섯 개 전부 기술 문장에 들어가는 순간 엉뚱한 곳을 가리킵니다. 번역은 일어났고, 그 과정에서 의미가 죽었습니다. 이 플러그인은 그 치환 사전을, 각각이 왜 실패하는지의 이유와 함께 싣고 있습니다.

<br/>

## 토큰 스캔으로는 할 수 없는 패스

위의 모든 패턴은 한 줄 안에서 보입니다. 깨끗한 스윕을 뚫고 살아남는 findings 는 한 줄을 **이웃과 대조해서** 읽을 때만 보이고, 사람 리뷰어가 가장 늦게 알아채는 것들입니다:

- **형제 구조 이탈** — 리스트의 bullet 하나가 나머지는 한 문장인데 혼자 두 문장이거나, 나머지는 결과로 시작하는데 혼자 동사로 시작합니다. 그 항목만 보면 멀쩡하고, 자리에 놓고 보면 틀렸습니다.
- **이웃 중복** — 같은 블록의 두 항목이 같은 것을 말합니다. 겹친다고 다 결함은 아닙니다: 접근 줄과 성과 줄에 기술명이 반복되는 건 군더더기가 아니라 필요한 것입니다. 이 플러그인은 세 갈래를 분류해 finding 인 하나만 보고합니다.
- **과장 드리프트** — 근거는 `방지` 인데 `차단` 이라고 쓰거나, 애초에 없었던 조건을 고쳐낸 결함처럼 서술하는 경우.
- **표기 일관성** — 한 문단에서는 `Pod`, 다음 문단에서는 `파드`. 대개 나중 편집이 파일의 관례가 아니라 글쓴이의 습관을 따랐기 때문입니다.
- **용어 도입 관례** — 다른 데서는 전부 `부분 장애(gray failure)` 로 쓰면서 `fail-fast` 만 맨 영어로 남은 경우. 표기 일관성 검사는 이걸 가볍게 통과시키지만, 문서 자신의 관례는 통과시키지 않습니다.

각각은 근거와 함께 보고됩니다 — 대조한 형제 줄, 또는 두 개의 카운트. 확인할 수 없는 finding 은 finding 이 아닙니다.

<br/>

## 모드 2개, 그리고 잘못 고르는 것이 흔한 실망

**감사** 는 스윕입니다: 파일이나 디렉터리를 가리키거나 아무것도 주지 않으면 모든 finding 을 분류해 돌려줍니다. 언제나 read-only 입니다 — 한 줄씩 읽어보지 않은 일괄 적용이야말로 그 제약이 막으려는 바로 그것입니다.

**판정** 은 하나에 대한 판정입니다: 문장을 고쳐 써 놓고 이게 나은지 알고 싶을 때. 항목을 형제들과 함께 *제자리에서* 읽고, 당신 버전이 이미 만들어낸 개선을 지키면서 무엇을 지켰는지 말해 주고, 병합된 줄을 적용할 수 있습니다 — 전/후를 전문으로 보이고 승인을 받은 뒤에.

문장 하나를 고쳐 들고 온 사람은 40건짜리 파일 감사를 원하지 않습니다. 호출이 애매할 때 이 플러그인은 한 줄로 묻고 판정으로 기본 처리합니다. 그쪽이 더 싼 오답이기 때문입니다.

<br/>

## 범위

범위 안: body 가 한국어 산문 위주인 모든 `.md`, 그리고 문자열이 `{ ko, en }` 쌍으로 된 YAML 파일의 `ko:` 절반.

범위 밖: `en:` 절반, `*-en.md`, 영어 `.md`, 코드 블록, inline code, URL, 파일 경로, 소스 파일의 주석. 양방향으로 한국어 전용입니다 — 한국어 변경에 맞추려고 영어를 고쳐 쓰지 않으며, 수정이 pair 의 parity 를 깨뜨리면 그렇다고 말합니다.

bilingual 파일에서는 `en:` 형제를 **먼저** 읽습니다. 이런 문서는 대개 EN → KO 로 작성되므로 한국어 절반이 열화된 쪽입니다: 목적어나 수식어, 단위가 번역 과정에서 떨어져 나가고 영어에는 아직 남아 있습니다. `QA delivery-time` 이 `QA 전달 90% 단축` 이 되면서 단위가 사라졌고, 실제로 줄어든 것은 시간이었습니다. 영어 절반에서 복원하면 재작성이 창작이 아니라 검증 가능한 것이 됩니다.

<br/>

## 절대 하지 않는 것

- 텍스트의 주장을 바꾸는 일. 숫자, 기술 레이블, 날짜, 화살표는 모든 재작성에서 살아남고, 틀려 보이는 사실은 flag 될 뿐 조용히 고쳐지지 않습니다.
- 감사 모드에서의 편집. 수정이 아무리 명백해 보여도 하지 않습니다.
- 전/후를 전문으로 보이고 승인받지 않은 판정 모드 편집 — 그리고 승인 1건은 항목 1건만 덮고 파일 전체는 절대 아닙니다.
- `en:` 절반이나 영어 문서를 건드리는 일.
- heading, 섹션, 리스트 항목, 표 행의 추가 / 제거 / 재정렬 / 병합 / 분할.
- 공백을 낀 em-dash 를 flag 하는 일. 기술 산문에서 그건 의도된 장치이고, 금지 규칙을 두면 진짜 finding 이 전부 묻힙니다.
