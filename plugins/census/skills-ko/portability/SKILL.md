# census:portability — 나는 실제로 무엇을 공유할 수 있나?

이 머신과 이 소유자를 식별하는 문자열을 도출하고, 그것이 agent / command / skill 안에서 나타나는 모든 위치를 찾아, 각 항목이 환경에 얼마나 깊이 묶여 있는지 등급을 매긴다.

이 skill 은 **읽기 전용** 이다. 등급을 매기고 설명할 뿐, 절대 수정 · 이동 · 승격하지 않는다.

<br/>

## 실행

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/census.py" portability --evidence 3
```

티어만 보고 싶으면 `--evidence 0` 으로 항목별 인용을 뺀다. `--json` 은 원본 리포트를 낸다. 사용자가 `$ARGUMENTS` 로 준 것은 그대로 전달한다.

스크립트 출력을 근거로 보고한다 — 직접 파일을 다시 스캔하지 말고, 스크립트의 표를 다시 옮겨 적지 않는다.

<br/>

## 마커는 어떻게 도출되나

하드코딩된 것은 없다. 마커는 스캔 대상 환경에서 나오며, 그래서 같은 검사가 다른 사람의 식별자도 잡아낼 수 있다:

| 카테고리 | 출처 |
|---|---|
| `user` | `$USER`, 홈 디렉터리 이름 |
| `layout` | 홈 아래 `projectRoots` 의 디렉터리 이름 — 사용자가 repo 를 정리하려고 만든 체계 |
| `account` | **공개** forge remote 의 owner 세그먼트 — 전역적으로 고유한 네임스페이스 |
| `host` | 자체 호스팅 forge 의 호스트명과 그 등록 가능 레이블 |
| `repo` | 각 repo 자신의 이름 — 그 repo 안에 있는 항목에 **한해서만** 매칭 |
| `configured` | config 의 `portability.markers` 에 넣은 모든 것 |

자체 호스팅 forge 에서 owner 는 그룹 이름일 뿐이고 흔히 일반 단어 (`server`, `infra`) 이므로, 대신 호스트를 취한다.

`repo` 카테고리가 전역이 아니라 범위 한정인 것도 같은 이유다. repo 범위 agent 는 보통 자기 repo 를 상대 경로로 지칭한다 — `Reviews changes inside acme-platform/storage/` — 여기에는 머신 전역 식별자가 하나도 없어서, 가장 이식성 낮은 항목 중 하나이면서도 완벽히 portable 하게 채점된다. 전역으로 적용하면 `docs` 나 `tools` 같은 repo 이름이 아무 산문에나 걸리지만, 자기 repo 로 한정하면 매칭은 말 그대로의 의미를 갖는다.

**알려진 사각지대: 이름 붙은 인프라.** 마커는 remote 와 루트에서 도출되므로, 클러스터 · 환경 · 네임스페이스 · 프로젝트 코드명은 아무것도 공급하지 않는다. 헌장이 repo 가 아니라 `prod-eu-1` 에 묶인 항목도 여전히 🟢 로 나온다. 🟢 항목의 description 이 환경 이름을 담고 있으면 분명히 말하고, 그 문자열을 `portability.markers` 에 추가하라고 알려준다 — 그 키가 존재하는 이유다. 🟢 목록을 읽지 않은 채 안전하다고 취급하지 않는다.

마커 표가 이상해 보이면 — 보편적인 것이 올라와 있거나 명백한 식별자가 빠졌으면 — 그렇다고 말하고 `portability.markers` 를 제안한다. 하위 등급 전부가 여기에 의존하기 때문이다.

<br/>

## 티어

등급은 마커가 몇 개인지가 아니라 **어디에** 떨어졌는지에서 나온다. 리뷰어가 근거만 보고 다시 도출할 수 있도록 규칙은 기계적이다:

| 티어 | 규칙 | 의미 |
|---|---|---|
| 🟢 `PORTABLE` | 매칭 없음 | 그대로 승격 |
| 🟡 `PARAMETERIZABLE` | 코드 스팬이나 코드 펜스 안에서만 매칭 | 결합이 리터럴이다 — config 값이나 환경 변수로 바꾼다 |
| 🔴 `PERSONAL` | frontmatter 나 산문에 매칭이 하나라도 있음 | 헌장 자체가 이 환경을 전제한다. 라우팅이나 범위를 설정이 아니라 **재작성** 해야 한다 |

frontmatter 케이스가 가장 중요하다: 특정 repo 를 지목하는 `description` 이 곧 Claude 가 라우팅하는 근거이므로, 그것을 바꾸면 항목이 언제 발동하는지가 바뀐다. 그것은 설정이 아니라 재작성이다.

**hook 은 그것이 실행하는 스크립트를 통해 등급이 매겨진다.** `settings.json` 의 등록은 포인터일 뿐이고, 하드코딩된 경로는 대상 파일 안에 있어서 등록만 읽으면 하나도 보이지 않는다. 커맨드도 셸 스크립트도 frontmatter 가 없으므로 hook 은 최대 🟡 에서 멈춘다 — 스크립트 안의 경로는 언제나 변수로 들어올릴 수 있는 리터럴이다. 매칭이 가장 많은 hook 이 무엇인지 보고한다: 한 사람의 디렉터리 배치에서만 발동하는 가드는 다른 누구에게도 조용히 아무 일도 하지 않는다.

<br/>

## 무엇을 보고하나

**1. 공유 가능 비율을 담백하게.** 낮은 숫자는 성숙한 개인 config 의 정상적인 결과이고 결함이 아니다 — 항목들이 상상 속 일반 환경이 아니라 실제 환경을 위해 쓰였다는 뜻이다. 그렇다고 말한다. 이 숫자는 승격 작업의 출발 지도이지 자책할 점수가 아니다.

**2. 🟢 목록은 전부.** 실행 가능한 부분이 여기다 — 이것들은 오늘 당장 손대지 않고 팀 플러그인에 넣을 수 있다.

**3. 품을 들일 만한 🟡 항목.** 각각에 대해 구체적으로 어떤 리터럴이고 무엇이 될지 지목한다 — config 키, 환경 변수, 인자. 가치가 높으면서 결합이 리터럴 한두 개인 항목을 우선하고, 열 몇 군데를 치환해야 하는 것은 넘긴다.

**4. 🔴 항목은 고치자고 제안하지 않는다.** 범위 *자체가* "이 특정 트리 아래의 repo 들" 인 agent 는 개인용인 것이 옳다. 일반화하라고 권하면 보통 더 나쁘고 더 모호한 agent 가 나온다. 무엇에 묶여 있는지만 말하고 멈춘다.

<br/>

## secret 스캐너가 아니다

이것은 "이게 다른 사람에게도 동작할까?" 에 답하지 "이게 뭔가 흘릴까?" 에 답하지 않는다. 둘은 겹치지만 어느 쪽도 다른 쪽을 포함하지 않는다:

- repo 배치 이름은 이식성이 없지만 무해하다.
- 비밀번호는 유출이지만 완벽하게 이식 가능하다.

사용자가 공개를 앞두고 있다면, 이식성 점검이 secret 스캔을 대신하지 못하며 둘 다 필요하다고 말한다.

<br/>

## 하드 룰

- 읽기 전용. 허용된 유일한 쓰기는 사용자가 요청한 명시적 `--out` 대상뿐이다.
- 더 portable 하게 만들려고 항목을 수정하지 않고, 이 skill 의 일부로 그렇게 하겠다고 제안하지도 않는다.
- 스캔 대상 트리에 절대 쓰지 않는다.
- 무엇도 플러그인이나 마켓플레이스로 승격하지 않는다 — 이 skill 은 등급 매기기에서 멈춘다.
- 마커를 손으로 다시 도출하거나 스크립트의 매칭 판정을 의심하지 않는다. 이상해 보이면 리포트가 아니라 config 를 고친다.
